# Linux shared dependency source and artifact review

## Scope and result

This review covers the 23 Linux CPython 3.13.5 x86_64 candidate artifacts assigned to the cross-role shared and unclassified partitions in `compel-resolution-comparison.json`. PyPI sdists and wheels were fetched from the published PyPI artifact URLs and checked against PyPI release JSON hashes. `torchcodec` is the CPython 3.13 cu129 wheel from the official PyTorch index; its source was inspected at upstream tag `v0.16.0`, commit `ce046a849e8a4054d7fee8879b7d574eb0e931c5`. For `kornia-rs`, the official upstream tag `v0.2.0` was inspected at commit `befcbe18b66f5fa71f5aea7745a1de1ffe4bdb8d`.

The wheel `RECORD` entries and recorded sizes/hashes validated for all 23 selected wheel files. Python files matched the corresponding sdist source byte-for-byte wherever the comparison tool found a source counterpart. ELF metadata was inspected statically; no wheel was imported or installed. The selected fixed `filelock` and `fsspec` pins have no exact-version OSV query matches in the collected results. OSV identified known advisories for prior candidate pins `filelock==4.0.12` (13 GHSA records) and `fsspec==2025.3.0` (GHSA-27vj-qcqg-25rc and PYSEC-2026-4217); the candidate uses `filelock==4.2.1` and `fsspec==2026.6.0` instead. Other exact pins returned no OSV matches in the query batch. This is advisory matching, not proof that code is safe.

**Activation disposition: hold.** The wheel notice reconciliation is now recorded in `packaging/licenses/kornia-rs-0.2.0-supplement/notice-manifest.json`, but OSV identifies reachable vulnerable dependency paths in the selected binary graph, and two selected crates are reported unmaintained. Do not activate this wheel until the applicable advisories and unmaintained dependencies have a reviewed disposition and the required rebuilt artifact is verified. The upstream wheel has not been modified.

## Findings and limits

- `filelock` and `fsspec` have had the exact vulnerable versions superseded by the fixed pins above. The newer pins preserve their locking and filesystem APIs; `fsspec` retains `ReferenceFileSystem` and now renders its templates through `jinja2.sandbox.SandboxedEnvironment`. Its supported Python floor rises to 3.10; `filelock`'s rises to 3.11. Both meet the candidate Python 3.13 target.
- `fsspec`, `httpx`/`httpcore`, and `diffusers` expose network-capable APIs when a caller requests remote files or model loading; no import-time network or telemetry behavior was observed in the inspected paths. `kornia` has explicit model/cache download helpers. Its optional `LazyLoader` can invoke `python -m pip install -U <module>` via an argument list when an optional dependency is missing and automatic mode is selected; default behavior prompts instead. `timm` can fetch pretrained weights when requested. These are feature-triggered paths, not executed during review.
- Source-build paths were inspected but not run. In particular, lxml's source build invokes system commands (including a `shell=True` subprocess path) and can fetch libxml2/libxslt in its static-dependency mode; SciPy's Meson build has source-fetch fallbacks; TorchCodec's CMake build fetches FFmpeg 4.4.4–9.0 and libavif 1.4.2 tarballs from PyTorch S3 with pinned SHA-256 values. TorchCodec's packaging scripts also use curl to retrieve FFmpeg/libavif source, without the CMake hash path. The selected binary wheel avoids these source-build hooks; they remain relevant if source builds are introduced.
- The TorchCodec wheel bundles several codec/image libraries and carries the included license files, including the NVIDIA CUDA EULA. Static ELF inspection also shows runtime dependencies on FFmpeg SONAMEs (`libavcodec`, `libavformat`, `libavdevice`, `libavfilter`, `libavutil`, `libsw*`), PyTorch libraries, and CUDA 12 libraries. Their host/runtime provenance is outside this wheel review and must be covered by the platform runtime inventory.
- Native wheel libraries in lxml, scikit-learn, SciPy, cffi, kornia-rs, xxhash, and TorchCodec were inspected using ELF dependency/RPATH metadata only; this does not establish runtime compatibility or behavior.
- Upstream `AGENTS.md` content in importlib-metadata, zipp, scikit-learn, and kornia-rs sources was treated as untrusted repository data. It was not followed as an instruction and was not present in the selected runtime wheel payloads.

No package installation, import, build hook, model download, network feature invocation, GPU operation, or audio playback was performed. The review does not validate application behavior, installed-system libraries, model files, runtime security, or performance. The exact candidate lock remains separately governed by its source-review and activation records.


## kornia-rs selected Linux Rust dependency notice and advisory follow-up

The selected wheel is `kornia_rs-0.2.0-cp313-cp313-manylinux_2_17_x86_64.manylinux2014_x86_64.whl`, SHA-256 `f8b71a0c0bc54ba7fc76f184d66a8f600c19754495313d245e8b28e847ef902e`. The exact source is upstream tag `v0.2.0`, commit `befcbe18b66f5fa71f5aea7745a1de1ffe4bdb8d`; the GitHub codeload archive at that commit is 4,964,051 bytes with SHA-256 `3f3307ed2c245103d6e1a377a4186003fe2e464d6cb65eb7ccfc2d3915105c24`. Its Cargo.lock is copied under `kornia-rs-0.2.0/` as source attribution evidence. `cargo tree --package kornia-py --target x86_64-unknown-linux-gnu --locked -e normal,build` selected 184 registry crates for the Linux wheel's normal/build graph (including default `turbojpeg`; CUDA was not enabled). Metadata resolution only; no Rust build script, install, test, import, or wheel execution was run.

The exact Cargo.lock checksum matched every downloaded `.crate` archive for the 184 selected registry crates. The source notice supplement preserves 330 files (1,573,983 bytes): 275 original license/notice/copyright files from checked crate archives; 13 selected crates whose archives omit standalone notices have license text copied from their exact `.cargo_vcs_info` revision; and `npyz==0.8.4`, whose exact source and archive provide only MIT SPDX metadata, has a clearly labeled canonical SPDX MIT reference text with no invented copyright attribution. Each record binds the selected Cargo.lock checksum and source archive hash to notice-file SHA-256 values. The manifest is a Rust-specific provenance sidecar; it has not been added to Python package configuration or the active dependency graph.

An exact-version OSV querybatch for all 184 selected crates returned matches for: `anyhow==1.0.102` (`RUSTSEC-2026-0190`), `bincode==2.0.1` (`RUSTSEC-2025-0141`, unmaintained), `paste==1.0.15` (`RUSTSEC-2024-0436`, unmaintained), `pyo3==0.28.3` (four advisories, fixed in 0.29.0), and `quick-xml==0.37.5` (`RUSTSEC-2026-0194` and `RUSTSEC-2026-0195`, fixed in 0.41.0). Source graph inspection confirms these dependencies are in the selected normal/build tree. In the reviewed path, `little_exif` parses image XMP with `quick_xml::Reader` and iterates `BytesStart::attributes()` with default checks, making the quadratic-attribute denial-of-service advisory relevant to untrusted image metadata. It does not use `NsReader`, so the namespace-allocation advisory path was not identified. Source search did not find kornia calls to PyO3's vulnerable `PyCFunction::new_closure` or `anyhow::Error::downcast_mut`; this does not establish that dependency APIs are unreachable in the compiled extension. `bincode` is used through `kornia-3d` and `kornia-apriltag`; `paste` is a selected proc macro through `faer`/`gemm`.

The notice supplement closes the source-notice collection work, but the exact selected wheel still contains the unresolved dependency graph described above. Any replacement must preserve kornia's API/features and be rebuilt and checked against the exact reviewed source and new lock before activation. The advisory query record is retained in the local review evidence; the source review does not claim clean OSV results or runtime validation.
